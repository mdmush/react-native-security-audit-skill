# Android project review

Covers the native Android half of the `platform` domain, plus Android-specific parts of `privacy`. Applies when `android/` exists. If it is generated by Expo prebuild and untracked, read [expo.md](expo.md) first: the source of truth is then the app config.

## Which files, which variant

Gradle merges manifests and resources per build variant. What ships in release is `src/main` + `src/release` + flavor directories + every library's manifest. `src/debug` never ships.

| File | Why it matters |
|---|---|
| `android/app/src/main/AndroidManifest.xml` | Components, permissions, backup, cleartext, deep-link filters for all variants |
| `android/app/src/debug/AndroidManifest.xml` | Debug only. Cleartext and overlay permissions here are expected |
| `android/app/src/main/res/xml/network_security_config.xml` (name varies; referenced by `android:networkSecurityConfig`) | Cleartext rules, trust anchors, pins |
| `android/app/src/main/res/xml/*backup*`, `data_extraction_rules.xml` | What backups include |
| `android/app/src/main/res/xml/*provider*paths*.xml`, `file_paths.xml` | What a FileProvider can hand out |
| `android/app/build.gradle(.kts)`, `android/gradle.properties`, `android/build.gradle` | Signing, minification, `debuggable`, SDK levels, repositories |
| `android/app/src/main/java/**` | `MainApplication`, `MainActivity`, custom modules, networking overrides |
| `android/app/proguard-rules.pro` | Whether shrinking is neutered by broad keep rules |

The merged manifest can contain components and permissions that appear in none of the app's own files, because libraries contribute them. You cannot see the merged result without building. When a finding depends on it, say so (`needs_validation`: "inspect `app/build/intermediates/merged_manifests/release/` or run `aapt dump xmltree` on the release APK").

## Manifest

**Exported components.** Since Android 12 every component with an intent filter must declare `android:exported`. `MainActivity` is exported by necessity. For every *other* exported activity, service, receiver or provider:

- Is it protected by a `android:permission` with `signature` protection level? If not, any installed app can start or bind to it.
- What does it do with the incoming `Intent` extras and data URI? Read the Kotlin/Java. A receiver that triggers a sync, a service that accepts a file path, an activity that skips the lock screen are `local-app` findings.
- Content providers: `exported="true"` with no permissions exposes whatever `query`/`openFile` returns. `grantUriPermissions` with broad path patterns is the quieter version.

**Deep-link filters.** `<data android:scheme="...">` under a `VIEW`/`BROWSABLE` filter. Custom scheme: any app can register the same one and the user gets a chooser, or no choice at all. `https` scheme: bound to the app only with `android:autoVerify="true"` *and* a matching `assetlinks.json` on the domain (outside the repo). What the links do is covered in [platform-entry-points.md](platform-entry-points.md).

**Backup.** `android:allowBackup` defaults to **true** when the attribute is absent. With it on and no exclusion rules, AsyncStorage, MMKV, databases and shared preferences are copied by cloud backup and device-to-device transfer, and on older Android versions by `adb backup`. On its own this is a hardening note. It becomes part of a finding when the app keeps tokens or sensitive data in those stores: cite it as the precondition that makes the data reachable. Proper exclusions are `android:dataExtractionRules` (API 31+) and `android:fullBackupContent` (older), or simply `allowBackup="false"`. Keystore-backed keys are never backed up, which can make restored encrypted data unreadable: note that when recommending encryption.

**Cleartext and trust.** `android:usesCleartextTraffic="true"` in the main manifest, or a network security config with `cleartextTrafficPermitted="true"` in `<base-config>`/`<domain-config>`. Also in the config: `<certificates src="user"/>` outside `<debug-overrides>` (trusts CAs the user was persuaded to install), and `<pin-set expiration="...">` dates in the past. How to rate these is in [network-and-auth.md](network-and-auth.md).

**`android:debuggable="true"`** written explicitly in the main manifest forces a debuggable release: anyone with USB access can attach a debugger and read app data with `run-as`. Normally Gradle controls this per build type and the attribute is absent. Check `buildTypes.release { debuggable true }` in Gradle as well.

**Task and activity settings.** `launchMode="singleTask"` on `MainActivity` is the React Native default, not a finding. Task hijacking concerns (`taskAffinity`) are hardening on current Android versions.

**Permissions** (`privacy`). List dangerous permissions and check each has a feature behind it: location (especially background), contacts, SMS, call log, microphone, camera, broad storage (`MANAGE_EXTERNAL_STORAGE`, legacy `WRITE_EXTERNAL_STORAGE`), `QUERY_ALL_PACKAGES`, `SYSTEM_ALERT_WINDOW`, `REQUEST_INSTALL_PACKAGES`. Unused permissions are privacy/hardening notes and a store-review risk, not vulnerabilities. Libraries add permissions silently; `tools:node="remove"` is the fix for unwanted ones. The Play Console Data safety form must match what the app and its SDKs actually collect and share; compare it with the analytics and crash SDK calls you found, and with whether those SDKs start before the user has consented. The form itself is outside the repo, so mismatches are `needs_validation` or hardening under `privacy`.

## Gradle and signing

- **Signing secrets.** Literal `storePassword`/`keyPassword` in `build.gradle`, or `*_STORE_PASSWORD=`/`*_KEY_PASSWORD=` in a tracked `gradle.properties`, together with a keystore file in the repo, is a `supply-chain` finding: a repo reader can sign builds as the app. With Play App Signing the upload key can be reset, which limits impact to the window before rotation; without it the key is the app's permanent identity. Ask which applies if it changes the rating. The template `debug.keystore` and its password `android` are public and irrelevant.
- **Release signed with the debug key.** `buildTypes.release { signingConfig signingConfigs.debug }` is what the React Native template ships, with a comment telling you to change it. If releases are really built that way, the app is signed with a key everyone has. More often the real signing happens in CI, EAS or Fastlane, and this block is unused. Check `eas.json`, `fastlane/`, and CI workflows before deciding; if you cannot tell, `needs_validation`.
- **Shrinking and obfuscation.** `minifyEnabled false` / `enableProguardInReleaseBuilds = false` is hardening. R8 does not protect the JS bundle in any case.
- **Repositories.** `jcenter()`, `http://` Maven URLs, or unpinned custom repositories in `build.gradle`/`settings.gradle` are supply-chain notes. An `http://` Maven repository with `allowInsecureProtocol = true` is a real dependency-substitution risk for whoever builds.
- **SDK levels.** A low `targetSdkVersion` disables platform protections (cleartext default-deny starts at 28, exported-by-default changes at 31). Note it when it changes another finding.

## Native code

Read `MainApplication`, `MainActivity` and anything under the app's package that is not template code.

- **Networking overrides**: `OkHttpClientProvider.setOkHttpClientFactory`, custom `TrustManager`/`HostnameVerifier`, `onReceivedSslError`. See [network-and-auth.md](network-and-auth.md). Check for a `BuildConfig.DEBUG` guard and which source set the class is in.
- **Custom native modules** (`@ReactMethod`, TurboModule specs): these are callable by the app's own JS, which is trusted. They become attack surface when JS forwards untrusted input to them (a WebView message or deep-link param passed to a module that reads files, runs commands, or starts intents). Look for file paths and `Intent` construction from arguments, `Runtime.exec`, reflection, and raw SQL.
- **WebView debugging**: `WebView.setWebContentsDebuggingEnabled(true)` without a debug guard.
- **Intents built from external data**: `startActivity(Intent.parseUri(untrusted))`, forwarding a received intent's extras into a new privileged intent, and mutable `PendingIntent`s handed to other apps.
- **Custom bundle loading**: an override of `getJSBundleFile()` that loads a bundle from external storage or a downloaded path without verifying a signature is code execution for whoever can write that file. See OTA in [supply-chain-and-release.md](supply-chain-and-release.md).
- **Logging**: `Log.d`/`Log.v` of tokens or request bodies in release paths.
- **Secrets in `strings.xml` or `BuildConfig`**: same rules as JS; see [secrets-and-config.md](secrets-and-config.md).

## Not findings

- Anything in `src/debug`, or guarded by `BuildConfig.DEBUG`.
- `MainActivity` exported with a launcher filter; `singleTask` launch mode.
- The debug keystore and its password.
- `allowBackup` enabled in an app that stores nothing sensitive in plaintext (hardening note).
- Disabled R8/ProGuard, absent root detection, absent `FLAG_SECURE` in an ordinary app (hardening notes).
- Permissions that a visible feature uses.
